# App privacy: technical data inventory

Prepared 2026-09-10 against source commit `27d04ce`. Scope: the native iPhone shell, its shared product components, and their Vercel/Neon server paths. This is preparation for the operator's Apple-account work, **not** a completed App Store privacy declaration, legal assessment, provider audit, or evidence of production retention settings.

Status vocabulary: **SOURCE** means observed in the implementation/schema; **CONDITIONAL** means the path requires configuration, entitlement or user action; **UNKNOWN** requires deployment/provider/operator evidence. Table categories are engineering descriptions, not preselected Apple questionnaire answers. Optional consent does not by itself make a disclosure optional.

the original brief remain in page memory, not persisted search snapshots or a

## Architecture and scope

- The app bundles the product UI separately from website SEO pages. Native requests use the configured HTTPS Sajda API origin; the website uses same-origin APIs. Both reach Vercel Functions and application-owned Neon PostgreSQL tables. Better Auth is a library running there, not a separate identity-hosting recipient. [Native shell](../src/app/NativeApp.tsx), [transport](../src/lib/nativeTransport.ts), [native plugin](../ios/App/App/SajdaNativePlugin.swift), [auth factory](../api/_shared/account-server.ts).
- Supabase-named legacy modules are not evidence of a live Supabase processor: the compatibility client has `hasSupabaseBrowserConfig = false` and no provider transport. Legacy cloud history/portfolio routes show an unavailable state, while Saved uses Neon. [Compatibility boundary](../src/integrations/supabase/client.ts), [route gate](../src/app/ProductRoutes.tsx), [Saved service](../src/lib/watchlistService.ts).
- Off-device requests always expose transport metadata to the receiving infrastructure even when no account is required. Hashing an identifier or omitting an email does not establish that a record is anonymous or unlinked.

## Deletion is a set of boundaries, not one universal erase

The implementation requires an authenticated request, a code sent to the account's stored email, and explicit confirmation. Only a committed deletion transaction reports success. Local auth cleanup is fenced against another account taking over during the request. Owner-bound auth, native/API credentials, Saved, research and commercial state are removed; shared catalogs, unlinked abuse counters/contact digests, provider records, mailboxes and backups are separate. [Service](../api/_shared/account-deletion.ts), [migration](../db/migrations/0015_account_deletion.sql), [client race handling](../src/contexts/AuthContext.tsx), [operational contract](ACCOUNT-DELETION.md).

Security lifetimes (two-minute codes, seven-day sessions, 15-minute deletion challenges) and freshness windows do not establish storage-retention promises. The few source-level pruning thresholds above describe code, not verified production purge execution.

## Operator verification gates before App Store declarations

1. **Freeze the actual release configuration.** Record backend domain, Vercel project/environment, Neon branch/region, enabled AI/Trading/native-commerce features, model/provider routes and third-party source list. Inspect production configuration without copying secrets into this document.
2. **Capture the real data flows safely.** On a physical device and sandbox account, inspect registration/recovery, search with AI off/on, Saved, Trading, contact, restore/purchase, share and deletion. Record destinations/field categories, not passwords, codes or bearer values. Unit tests and simulator appearance do not prove deployed collection behavior.
3. **Confirm infrastructure and recipient practices.** Obtain current Vercel/Neon/Resend/Google/Stripe/Apple arrangements and relevant registry/feed terms: regions, subprocessors, diagnostics, content retention, backups, deletion handling, access controls and cross-border processing. Also verify support-mailbox access/retention and provider delivery settings.
4. **Reconcile deletion and retention.** Verify production cascades, Stripe recovery path, Apple cancellation notice, token revocation, real email delivery, cron pruning, and restore-from-backup procedures. Define an owner-reviewed retention schedule and support process; do not substitute the implementation's validity timers.
5. **Audit the final iOS archive and hosting injection.** Inspect included SDKs and privacy manifests/required-reason API report, permissions, domains, telemetry, crash reporting and any web analytics injection. No first-party `PrivacyInfo.xcprivacy` was found by this source-file inventory; that does not establish what the compiled archive or dependencies contain. No camera/location/contacts/tracking permission prompt was identified in the inspected application `Info.plist`; verify the actual release archive.
6. **Make the human declaration decisions.** Using the evidence above, the operator must determine Apple's exact data types, purposes, account linkage, tracking and third-party disclosures, publish a matching privacy policy, and keep both current. Do not auto-select “Data Not Collected,” treat AI opt-in as an exemption, or infer an Apple answer from an engineering hash/local-cache label.

Reference for that final operator review: [Apple — App privacy details](https://developer.apple.com/app-store/app-privacy-details/). This document deliberately leaves the questionnaire unanswered.
