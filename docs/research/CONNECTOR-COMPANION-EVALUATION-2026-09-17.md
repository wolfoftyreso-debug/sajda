## Enablement and consent boundaries

The MCP implementation makes no enablement claim merely from `prompts/get`, `resources/read`, initialization or tool discovery. Companion prompt text says that it enables offers only when explicitly selected and applied, and expressly excludes retrieval for inspection. The guide repeats that connection and metadata reads do not authorize a search. This is consistent with MCP's [user-controlled prompt model](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts).

However, the protocol returns prompt messages with `role: "user"`; that role alone is not evidence of a real user's authorization. A host must preserve how the prompt was invoked. The server cannot distinguish a user applying the prompt from a client merely fetching identical metadata. Treating returned user-role text as independent permission would be a host integration defect.

The general policy allows a direct explicit Sajda naming request to authorize a search. The guided `find-business-names` prompt starts a brief/acceptance flow, but does not execute anything when fetched. Its direct-request exception should be retained so that actual explicit requests do not produce repeated permission questions.

Consent remains a host behavior requirement. There is no server-verifiable consent token or background intent endpoint, and a valid tool request can execute without the server seeing the preceding conversation. The SDK tests establish static metadata, argument validation, error codes and absence of provider work during metadata requests; they do not certify user consent or host model obedience.

## Findings and resolution

1. **Resolved in shared policy:** opt-in now expressly gates unsolicited suggestions; direct explicit requests do not require it.
2. **Resolved in shared policy:** hard-budget routing checks tool availability and forbids silent connection switching.
3. **Resolved in shared policy:** broad withdrawal disables conversation-wide offers and respects supported host preferences without promising cross-chat memory.
4. **Resolved in shared policy:** a one-sentence brief is shown before a contextual offer. The direct-request exception remains, so one meaningful authorization suffices.
5. **Resolved in source skill and built kit:** the authored skill initially duplicated the earlier instructions and reintroduced findings 1–4. The reviewed skill and expanded host templates now contain the corrected direct-request, brief, broad-decline and available-tool rules.
6. **Minor follow-up:** the skill explicitly handles disconnection and failure; shared policy explains missing tools but does not yet say to disclose provider/search failures. Carry the skill's failure instruction into shared policy for clients consuming only MCP instructions. Structured tool errors already exist; this is instruction consistency, not a missing error response.

These are instruction-level gaps and ambiguity, not observed third-party host failures. No protocol handler automatically starts a search, accepts a transcript as a prompt argument, subscribes to conversations or enables monitoring.

## Distributable package review

Reviewed the populated [source kit](../../integrations/sajda-connector): root portable plugin/MCP JSON, compatibility packaging, focused naming skill, README and Cursor/Replit/Lovable instruction templates. README correctly separates connection from optional companion activation, instructs users to preserve existing host configuration, and does not claim a universal ZIP upload route, installed connection, directory approval or completed host test.

The three source host templates contain the build-time `SAJDA_HOST_POLICY` marker. This is documented in README: users must install the built, expanded files rather than raw source templates. Expansion from the shared policy keeps the corrected consent and routing rules aligned.

Inspected the generated ZIP at `tmp/public-connector-release/.vercel/output/static/downloads/sajda-connector.zip` using the platform ZIP reader. It contained the expected 14 text files, including dot-prefixed compatibility manifests. The three host instructions and the naming skill included the corrected rules. No unresolved marker comments or TODO placeholders remained; README's descriptive reference to the marker is intentional. The computed ZIP SHA-256 matched both the checksum file and `connector.json`. The public configurations specify the public endpoint without credential headers. The manifest correctly records `host_install_e2e_verified: []`, `directory_approval: "not_claimed"` and `background_chat_access: false`.

Cursor's `alwaysApply: true` and Replit/Lovable instruction placement make the policy available to their host, but cannot guarantee a particular model's timing or obedience. The templates say applying the rule enables offers, not searches. No template says merely reading the MCP prompt/resource grants consent. The source skill discrepancy has been corrected.
